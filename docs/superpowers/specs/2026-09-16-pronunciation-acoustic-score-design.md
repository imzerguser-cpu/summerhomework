# 발음 정확도 자체 채점 (MFCC+DTW 음향 신호 비교) - 설계

## 배경
텍스트 매칭 기반 정답 판정(`checkAnswer`)은 브라우저 내장 음성인식(STT)이 "무슨 단어를 말한 것 같은지" 추측한 결과를 비교할 뿐이라, 발음이 나빠도 언어모델이 문맥으로 보정해 정답 처리되는 경우가 있고, 반대로 발음이 괜찮아도 오인식될 수 있다. 즉 텍스트 판정만으로는 "발음이 실제로 정확한지" 평가할 수 없다.

유료 발음평가 API(Azure Pronunciation Assessment 등)는 이 문제를 정확히 풀어주지만 카드 등록이 필요해 제외. 대신 브라우저 안에서 완전 무료로 학생의 실제 녹음과 원어민 음원의 음향 신호(MFCC)를 직접 비교하는 자체 채점을 추가한다.

## 적용 범위 (중요 제약)
- 원어민 실제 녹음(mp3, `AUDIOS[item.listenAudioKey]`)이 있는 "단어" 문제 + 마이크로 답한 경우에만 동작.
- **3·4학년 엔진에는 151개 단어에 실제 녹음이 있지만, 5·6학년 엔진(`AUDIOS`)에는 실제 녹음이 단 하나도 없다(전부 TTS).** 따라서 이 기능은 현재 **사실상 3·4학년 전용**이며, 5·6학년에서는 항상 조용히 비활성 상태로 유지된다(에러 없음, 그냥 점수가 안 뜸). 5·6학년에도 적용하려면 원어민 녹음 콘텐츠 자체를 추가해야 한다 — 이건 이번 스코프 밖.
- 문장 문제, 텍스트 입력 폴백, `MediaRecorder`/`AudioContext` 미지원 브라우저에서도 항상 비활성.

## 판정에는 반영하지 않음 (단계적 적용, 승인된 방향)
정답/오답 판정은 기존 텍스트 매칭(`checkAnswer`) 그대로 유지. 점수는 판정 후 `feedback` 영역 아래 `#pronScore` 배지("🎯 발음 정확도: NN%")로만 추가 표시되는 보조 정보다.

## 동작 흐름
1. `startListening()`에서 `recognizer.start()`와 거의 동시에 `startPronunciationCapture()`를 호출해 `getUserMedia` + `MediaRecorder`로 같은 마이크 소리를 녹음(음성인식과는 별개의 캡처 — SpeechRecognition은 자체적으로 마이크를 관리해서 스트림에 직접 접근할 수 없음).
2. `recognizer.onresult`에서 최종 결과가 나오면(`res.isFinal`) 기존 `markResult(...)` 호출과 별도로 `stopPronunciationCapture()`로 녹음을 마무리하고 `computeAndShowPronunciationScore(item, blob)`를 비동기로 실행(메인 정답/오답 흐름을 막지 않음).
3. `computeAndShowPronunciationScore`: 대상 문제에 `listenAudioKey`가 없으면 즉시 종료. 학생 녹음 blob을 `AudioContext.decodeAudioData`로 디코딩 → RMS 에너지가 너무 낮으면(무음/캡처 실패로 추정) 종료 → 원어민 mp3를 (최초 1회만, 캐시) 같은 방식으로 디코딩 → 두 신호를 MFCC(멜 특징) + DTW(시간축 정렬)로 비교해 0~100 점수 산출 → `#pronScore`에 색상 구간(good/mid/low)과 함께 표시.
4. `recognizer.onerror`에서도 캡처를 정리해 마이크 스트림이 남지 않도록 함. 다음 문제로 넘어가면(`renderQuestion`) 점수 배지를 초기화.

## MFCC+DTW 구현
순수 JS, 외부 라이브러리/서버/API 없음:
- 프레이밍(25ms/10ms) → 해밍 윈도우 → 라디언-2 FFT → 멜 필터뱅크(26개) → 로그 → DCT(13계수, 0번 계수는 전체 음량이라 비교에서 제외)
- DTW로 두 MFCC 시퀀스를 정렬해 평균 프레임당 거리 산출(속도 차이는 DTW가 흡수)
- 거리 → 점수는 지수 감쇠(`100 * exp(-distance/30)`)로 변환. 선형 클램프는 "많이 다른 경우 전부 0점"으로 뭉개져서(합성 신호 테스트에서 확인) 등급을 못 나눴기 때문에 지수 감쇠로 바꿈.

## 검증한 것 / 아직 검증 못 한 것
- **검증함**: 합성 신호(사인파 기반 포먼트 흉내)로 동일 신호=100점, 속도만 다른 동일 "단어"=90점대(느려도 DTW가 잘 흡수), 완전히 다른 신호=낮은 점수로 잘 갈리는 것을 확인. Playwright에 `--use-fake-device-for-media-stream`을 붙여 실제 브라우저에서 캡처→디코딩→MFCC→DTW→UI 표시까지 전체 파이프라인이 에러 없이 동작하고 점수가 뜨는 것도 확인(3·4학년 엔진, 실제 원어민 mp3 대상). 3·4/5·6학년 양쪽에서 기존 회귀 스위트(`scripts/verify.js`)와 3회-오답 선택지 기능 모두 그대로 통과.
- **검증 못 함**: 실제 사람 목소리로 "이 점수가 진짜 발음 품질을 잘 반영하는지"는 자동화로 확인할 수 없음. `tau=30`(거리→점수 변환 상수)은 합성 신호 기준으로 고른 시작값이라, 실제 사용해보면서 재조정이 필요할 가능성이 높음. 배경 소음/녹음 볼륨 차이에 점수가 민감하게 반응하는 것도 확인됨(합성 테스트: 같은 발음에 잡음만 추가해도 93점 → 37점으로 하락) — 이 부분은 실사용 중 관찰이 필요.

## 테스트 방법
- `node scripts/build.js && node scripts/verify.js` 통과 확인.
- 3·4학년에서 원어민 녹음이 있는 단어 문제를 마이크로 답하면 "🎯 발음 정확도: NN%" 배지가 뜨는지, 다음 문제로 넘어가면 사라지는지 실제 브라우저에서 확인.
- 5·6학년에서는 배지가 절대 뜨지 않는 것(의도된 동작)을 확인.
- 여러 번 답해보며 점수 체감이 너무 박하거나 후한지 확인하고 `tau` 상수 재조정.
